# Stage discovery: drop a file in `src/stages/`, get a node kind

Date: 2026-09-23 · Status: draft for review

## Goal

Adding a stage should mean creating one file in `src/stages/` and running
`cargo build`. No edits to `stages/mod.rs`, `exec/registry.rs`, or any other
list of stages.

Success criteria:

1. A new file `src/stages/foo.rs` with a `register` fn is compiled and its
   kind(s) appear in `builtin_registry()` on the next build, with no other file
   touched.
2. Deleting that file removes the kind on the next build, again touching
   nothing else.
3. Every existing kind (`crop`, `cast`, `split`, `merge`, `blend`,
   `image_read`, `image_write`, `clear_channel`, `grayscale`, `invert`) keeps
   its name and params, so existing pipeline files load unchanged.
4. Two files registering the same kind is a loud failure, not silent shadowing.
5. Both CI legs (headless, `bevy`) pass fmt, clippy `-D warnings`, and tests.

Non-goals (later work, noted so the design does not block them):

- **Runtime plugins** (compile/load stages while running). The per-file
  `register(&mut Registry)` contract below is deliberately the same shape a
  dynamic-library plugin would export, so a future plugin loader is a second
  caller of the same contract, not a redesign.
- **GPU stages** (CUDA etc.). The registration contract is payload-agnostic
  (`Box<dyn Node>`); GPU work will additionally need a device-resident
  `Payload` variant so frames do not round-trip to host memory per stage.
  Out of scope here.

## Design

### The per-file contract

Each stage module exposes exactly one required item:

```rust
pub fn register(reg: &mut Registry)
```

It owns its kind string(s) and constructor. A file may register several kinds
(`image_io.rs` registers `image_read` and `image_write`). A file missing
`register` is a compile error that names the module.

Two helpers on `Registry` keep this to one line for the common cases:

```rust
/// Register a `Node` built from params via `TryFrom<&Params>`.
pub fn register_stage<T>(&mut self, kind: &str)
where
    T: Node + for<'a> TryFrom<&'a Params, Error = BuildError> + 'static;

/// Register a `Processor` wrapped in `ProcessorNode` (ports `in` -> `out`).
pub fn register_processor<P, F>(&mut self, kind: &str, ctor: F)
where
    P: Processor + 'static,
    F: Fn(&Params) -> Result<P, BuildError> + 'static;
```

Both helpers **panic on a duplicate kind** (`"node kind 'blend' registered
twice"`). The registry is built at startup, so this surfaces immediately and
is covered by a test. The existing `Registry::register` keeps its
replace-on-duplicate behaviour for callers that intend to override a kind.

Example, the whole registration for `blend.rs`:

```rust
pub fn register(reg: &mut Registry) {
    reg.register_stage::<BlendStage>("blend");
}
```

### Discovery: `build.rs`

A new `build.rs` (standard library only, no new dependencies):

1. Lists `src/stages/`. A module is either `name.rs` (other than `mod.rs`) or
   a directory `name/` containing `mod.rs` (for stages that need several
   files).
2. Sorts module names so output is deterministic.
3. Rejects names that are not valid Rust identifiers with a build error naming
   the file.
4. Writes `$OUT_DIR/stages_gen.rs`:

   ```rust
   #[path = "C:\\...\\src\\stages\\blend.rs"]
   pub mod blend;
   // ...one per module...

   /// Register every stage module's kinds. Generated by build.rs.
   pub fn register_all(reg: &mut crate::exec::Registry) {
       blend::register(reg);
       // ...
   }
   ```

   Paths are absolute and emitted with Rust string escaping (`{:?}`), which is
   what keeps Windows backslashes valid inside the literal.
5. Emits `cargo:rerun-if-changed=src/stages` (Cargo rescans the directory, so
   adding or removing a file reruns the script) and
   `cargo:rerun-if-changed=build.rs`.

The build script never parses Rust; it only lists files. All checking is done
by the compiler.

### `src/stages/mod.rs`

Becomes static: module docs (including "how to add a stage") plus

```rust
include!(concat!(env!("OUT_DIR"), "/stages_gen.rs"));
```

It is never edited when a stage is added.

The flat re-exports (`stages::SplitStage`) go away; types are reached through
their module (`stages::split::SplitStage`). Glob re-exports are not generated
because every module exports a function named `register`, which would make
the globs ambiguous (`ambiguous_glob_reexports`, fatal under `-D warnings`).
Nothing outside the crate imports stage types today, so this breaks no users.

### `builtin_registry()`

Shrinks to:

```rust
pub fn builtin_registry() -> Registry {
    let mut reg = Registry::new();
    crate::stages::register_all(&mut reg);
    reg
}
```

The imports of every stage type in `exec/registry.rs` are removed.

### Processors move into `stages/`

`clear_channel.rs`, `grayscale.rs` and `invert.rs` move from `src/processors/`
to `src/stages/` and gain `register` fns using `register_processor`, so there
is one rule for "a kind the runtime knows about". `ProcessList` is a
combinator, not a registered kind; it stays in `src/processors/` (which then
holds only it). The `Processor` trait stays in `src/traits/`.

### Tests

- `exec::registry` test: `builtin_registry()` contains exactly the ten existing
  kinds (catches a stage dropped by the move or discovery).
- `exec::registry` tests: `register_stage` / `register_processor` panic on a
  duplicate kind; `register` still replaces.
- Unit tests stay in their stage files; the split→merge round-trip test in
  today's `stages/mod.rs` moves to `tests/pipeline_execution.rs` (it exercises
  two stages together).
- Existing integration tests run unchanged (they go through the registry).
- Manual check of the headline workflow, recorded in the plan: add a
  throwaway `src/stages/passthrough.rs`, `cargo run -- check` a YAML that uses
  `kind: passthrough`, delete the file, confirm the kind is gone. Not kept as
  an automated test, since it would have to write into `src/` during the test.

### Docs

README "Architecture" gains a short "Adding a stage" section showing the file
template above; `stages/mod.rs` docs carry the same template.

## Risks

- **IDE support:** rust-analyzer resolves `include!` of `OUT_DIR` files once
  build scripts are run (its default), so go-to-definition keeps working. If
  it is disabled, stage files still compile; only the IDE view degrades.
- **Silent non-registration:** impossible by construction; every discovered
  module's `register` is called, and a module without one fails to compile.
